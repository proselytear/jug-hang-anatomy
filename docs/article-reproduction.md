# Воспроизведение опытов статьи

Статья использует два исторических снимка: `457542776c916e55fefe63fddd8ce88dbd6a3b9a`
для исходного приложения и `8c14914cb6b5533614cfae6e1035fe61c5a4c1de` для короткой
транзакции и защит. Новые исправления журналирования, метрик исполнителей и старта
Hikari не подменяют эти измеренные версии. Все времена в данных указаны в UTC.

## Два пути запуска

Штатный сценический запуск:

```bash
git clone https://github.com/proselytear/jug-hang-anatomy.git
cd jug-hang-anatomy
make up
make partner-slow
make test-mixed-load
make dashboard-urls
```

Нужны Git, Docker с Compose, make, curl и rg. `make up` включает
`docker,demo-latency`. `make test-mixed-load` использует JMeter из репозитория.
Параметры команд сравнения должны совпадать. Это не генератор клиентских таблиц
статьи: для них используется `tools/article/closed_loop.py`.

Для измерения чистого замедления HTTP используется только `docker`.
`demo-latency` дополнительно удерживает JDBC внутри транзакции и замедляет
служебные запросы. Сравнивать эти условия как одно изменение партнёра нельзя.

## Изолированные копии вместо переключения рабочего каталога

Следующие команды выполняются из копии новой версии репозитория, содержащей
`tools/article/`. Они создают соседние каталоги, а исходный рабочий каталог не
переключают. Для нового опыта выберите другое имя проекта, свободные порты и
свободную подсеть, если она задаётся явно.

```bash
git clone https://github.com/proselytear/jug-hang-anatomy.git ../hang-baseline
git -C ../hang-baseline switch --detach 457542776c916e55fefe63fddd8ce88dbd6a3b9a
git clone https://github.com/proselytear/jug-hang-anatomy.git ../hang-main-measured
git -C ../hang-main-measured switch --detach 8c14914cb6b5533614cfae6e1035fe61c5a4c1de
python3 tools/article/prepare.py --source ../hang-baseline \
  --out ../hang-runtime --project hang-article --legacy-pool-name
export ARTICLE_COMPOSE="$(cd ../hang-runtime && pwd)/compose.json"
docker compose -f "$ARTICLE_COMPOSE" up -d --build
curl -fsS http://127.0.0.1:18080/actuator/health/liveness
curl -fsS http://127.0.0.1:18080/api/v1/demo/config
```

`prepare.py` получает развёрнутый Compose, создаёт отдельные контейнеры, сеть и
тома. Опубликованные порты привязаны к loopback. По умолчанию приложение доступно
на `18080`, Grafana на `13000`, WireMock на `18089`, PostgreSQL на `15432`.
Остальные порты: Mimir `19009`, Loki `13100`, Tempo `13200`, Alloy OTLP
`14317/14318`, интерфейс Alloy `22346`. `--port-offset` меняет смещение всех
публикуемых портов. Если Docker сообщает об исчерпанных пулах адресов, можно
передать `--subnet` с заранее проверенной свободной подсетью.

Контейнеры PostgreSQL и WireMock получают по 2 CPU, приложение 2 CPU и 1536 MiB.
Параметры JVM: `-XX:MaxRAMPercentage=70 -Dfile.encoding=UTF-8`.
Для чистой пары исходного и короткого вариантов задаются Tomcat 16,
Hikari 6, ожидание соединения 12000 мс, HTTP read timeout 15 с и общий бюджет 15 с.
Все пять переключаемых защит первоначально выключены.

Для короткого варианта подготовьте отдельный проект из `../hang-main-measured`
с другими портами или остановите только предыдущий изолированный проект.
В `source.json` сохраняются коммит, профиль и факт адаптации старой конфигурации.
Файл `compose.json` содержит все действующие параметры запуска.

## Почему историческому Hikari нужна внешняя конфигурация

На чистом образе `8c14914` запуск только с переменными окружения воспроизвёл
ошибку привязки `spring.datasource.hikari.pool-name`. Hikari уже запущен,
поэтому `setPoolName` отклоняется как изменение sealed configuration.
Остановка на первом `HikariDataSource.getConnection()` показала в стеке
`JavaBeanBinder$BeanProperty.lambda$getValue$0`: Spring читает JavaBean-свойство
при биндинге, получает соединение и запускает пул раньше установки имени.
Это отличается от предположения о раннем запуске через Flyway.

Доказательства сохранены в `evidence/startup-env-only/`. Новая версия задаёт
имя через `spring.datasource.name: hang-hikari`, до привязки свойств Hikari.
Поэтому её штатный `make up` не требует внешней копии YAML.

Для неизменённых исторических коммитов `--legacy-pool-name` автоматизирует
процедуру измерений: копирует `application*.yml` в каталог запуска, убирает
`hikari.pool-name`, добавляет `spring.datasource.name` и задаёт
`SPRING_CONFIG_LOCATION=file:/article-config/`. Java-код и JAR исходного снимка
не меняются. Использовать этот флаг с новой исправленной версией не требуется.
Флаг намеренно завершается ошибкой, если историческая строка уже отсутствует.

## Профили и искусственные задержки

| Параметр `8c14914` | Базовый YAML | `demo-latency` | Чистое сравнение |
| --- | --- | --- | --- |
| Tomcat | 32 | 16 | 16 |
| Hikari | 10 | 6 | 6 |
| Ожидание соединения | 750 мс | 12 с | 12 с |
| HTTP read timeout | 1,8 с | 15 с | 15 с |
| Общий бюджет | 2 с | 15 с | 15 с |
| TimeLimiter при включении | 1,5 с | 12 с | выключен |
| Partner Bulkhead | 8 | 8 | выключен |
| TTL admin/readiness | 5 с | 0 с | 5 с в main |
| Бюджет admin/readiness | 250 мс | 12 с | 250 мс в main |

В `demo-latency` режим `slow-partner` означает HTTP 5000 мс,
ожидание 1500 мс внутри транзакции чтения и по 2000 мс для admin/readiness.
В базовом профиле последние три искусственные задержки выключены.
Режим `tx-hold` добавляет 1500 мс после SQL внутри транзакции при быстром
партнёре. Это опыт на время владения JDBC, а не модель конкретного медленного SQL.

## Переключение режима и контрольные запросы

Менять нужно и WireMock, и режим приложения. Скрипты уже выполняют обе операции:

```bash
APP_URL=http://127.0.0.1:18080 WIREMOCK_URL=http://127.0.0.1:18089 \
  ./scripts/wiremock/set-normal.sh
APP_URL=http://127.0.0.1:18080 WIREMOCK_URL=http://127.0.0.1:18089 \
  ./scripts/wiremock/set-slow.sh
curl -sS --max-time 45 -w '\nHTTP %{http_code}, %{time_total}s\n' \
  http://127.0.0.1:18080/api/v1/dashboard/00000000-0000-0000-0000-000000000001
curl -sS http://127.0.0.1:18080/actuator/health
curl -sS http://127.0.0.1:18080/actuator/health/readiness
curl -sS http://127.0.0.1:18080/actuator/health/liveness
```

Для опыта с резервным ответом предварительно получите успешный dashboard при
быстром партнёре, чтобы в PostgreSQL появился снимок данных. Начальное состояние
Circuit Breaker фиксируйте отдельно. Перезапуск приложения очищает локальное
состояние автоматов, но сохранённый в томе снимок остаётся.

## Генератор и методика

```bash
python3 tools/article/closed_loop.py evidence/my-baseline-slow \
  --base http://127.0.0.1:18080 --heavy 12 --admin 1 --health 1 \
  --warmup 10 --duration 60 --pace 1 --probes
```

Полный исполняемый генератор расположен в `tools/article/closed_loop.py`.
Он использует только стандартную библиотеку Python 3. Каждый работник выполняет
один запрос за раз. `pace=1` задаёт минимальный интервал между началами его
запросов. После медленного ответа следующий начинается позднее. Это закрытая
модель с совместным стартом работников, без случайного разгона. При 429 темп
также ограничен, чтобы не создавать неограниченные мгновенные повторы.

Прогрев и измерение идут одним составом работников. Принадлежность определяется
по началу запроса. Запрос прогрева исключается из основной сводки даже тогда,
когда завершился уже внутри измерительного окна. По окончании окна новые
запросы прекращаются, отправленные дожидаются ответа или клиентского тайм-аута
45 с. Поэтому количество запусков за 60 с и достигнутый RPS с завершающим
интервалом обозначают разные величины.

Сохраняются `requests.jsonl` с началом, окончанием, длительностью, статусом,
транспортной ошибкой и телом ответа, `window.json`, `summary.json`,
`scrape-events.jsonl`, отдельные `scrape/*.txt`.
Опрос `/actuator/prometheus` выполняется раз в секунду с тайм-аутом 4 с.
С `--probes` отдельно работают readiness/liveness раз в 5 с.
Пропуск опроса сохраняется как ошибка. Из него не создаётся нулевая точка.

Перцентили вычисляются линейной интерполяцией между соседними отсортированными
значениями. Для каждого маршрута отдельно учитывайте статусы, `outcome` и
`partner.source`. Совокупный p95 способен уменьшаться за счёт быстрых отказов
или резервных ответов, поэтому публикуйте также задержку свежих результатов.
Медианы метрик по успешным опросам описывают полученные точки, а не среднее,
взвешенное по времени. Grafana использует отдельный сбор Alloy раз в 5 с.

До запуска сохраните `passport.json`: полный SHA, профиль, полный набор env,
лимиты CPU/памяти, образы и JVM, WireMock mappings, режим приложения, нагрузку,
прогрев, окно, адреса и начальное состояние снимка/автоматов. Сохраните Compose
рядом с ним. Не помещайте в публичный паспорт рабочие секреты.

Для повтора одной волны тайм-аута настройте `TimeLimiter` 1 с, общий бюджет 3 с,
HTTP read timeout 8 с, partner Bulkhead 8, включите Circuit Breaker и отключите
DB Bulkhead/Rate Limiter. Нужны предварительно сохранённые данные при быстром
партнёре, новый процесс с чистым автоматом и затем WireMock 5000 мс.

```bash
python3 tools/article/timeout_wave.py --out evidence/my-timeout-tail \
  --compose "$ARTICLE_COMPOSE" --base http://127.0.0.1:18080
python3 tools/article/analyze.py my-baseline-slow
```

`timeout_wave.py` отправляет восемь запросов один раз, сохраняет дамп через
две секунды после последнего ответа и опрашивает ресурсы до завершения HTTP.
Параметры среды и предварительные действия нужно записать в паспорт до запуска.
Исходные версии скриптов фактических прогонов хранятся в `evidence/harness/`.
Копии в `tools/article/` принимают переносимые адреса и путь Compose.

## Дампы JVM и PostgreSQL

```bash
docker compose -f "$ARTICLE_COMPOSE" exec -T app jcmd -l
```

Из вывода выберите PID Java-процесса. В разных образах он отличается:

```bash
ARTICLE_JVM_PID=9
docker compose -f "$ARTICLE_COMPOSE" exec -T app \
  jcmd "$ARTICLE_JVM_PID" Thread.print -l > threads-1.txt
docker compose -f "$ARTICLE_COMPOSE" exec -T postgres \
  psql -U hanganatomy -d hanganatomy -P pager=off -c \
  "SELECT now() AT TIME ZONE 'UTC' AS sampled_utc, pid, state,
          wait_event_type, wait_event,
          clock_timestamp() - xact_start AS tx_age,
          clock_timestamp() - query_start AS query_age,
          left(query,160) AS query
   FROM pg_stat_activity
   WHERE datname = current_database() AND pid <> pg_backend_pid()
   ORDER BY xact_start NULLS LAST;" > pg_stat_activity-1.txt
```

Выполните 2–3 раза во время нагрузки с разными именами файлов.
Пользователь и БД здесь `hanganatomy`, как в Compose. `idle in transaction`, возраст
транзакции и последнее SQL-чтение сопоставляются с Hikari и сетевым стеком JVM.
Отдельный поздний дамп после измерительного окна сохраняйте с собственной
временной отметкой. Третий дамп старой серии, 10:50:18 UTC, уже был позже окна
`baseline-slow`, завершившегося 10:49:51.614 UTC.

## Сохранённые данные и граница независимой проверки

Новые измерения 29 октября находятся в `evidence/` с паспортами и исходными
файлами. Числа 23 октября перенесены без изменений из опубликованного DOCX.
Первичные JSONL и полные дампы старой временной папки не сохранились. Это
ограничение независимой проверки старых чисел, а не основание создавать
восстановленные JSONL. В `evidence/v4-published/` находятся сам DOCX, его SHA256,
опубликованные агрегаты и происхождение. На общем графике источники различаются.

## Завершение опыта

```bash
docker compose -f "$ARTICLE_COMPOSE" stop
```

Команда останавливает только подготовленный изолированный проект и сохраняет
его тома. Повторное использование данных и автоматов должно быть явно указано
в паспорте следующего запуска.
